Normalização de Banco de Dados

Como organizar informações em tabelas relacionadas para reduzir repetições e manter a consistência dos dados.

Desnormalização

1. Por que organizar um banco de dados?

Imagine uma loja virtual que registra clientes e seus pedidos. Se todas as informações forem colocadas em uma única tabela, o nome e o e-mail de um cliente poderão aparecer repetidos em várias linhas. Isso aumenta a chance de inconsistências e torna alterações mais trabalhosas.

A normalização ajuda a organizar essas informações em tabelas com responsabilidades bem definidas. Neste artigo, vamos usar um exemplo simples de loja virtual para entender o conceito e conhecer as três primeiras formas normais.

2. O que é normalização?

Normalização é o processo de organizar os dados de um banco de dados em tabelas relacionadas, seguindo regras chamadas formas normais. O objetivo é reduzir repetições desnecessárias e evitar problemas na inclusão, alteração e exclusão de registros.

Em palavras simples: em vez de guardar os mesmos dados em vários lugares, cada informação fica preferencialmente no local adequado e é relacionada às demais por meio de identificadores, como chaves primárias e estrangeiras.

A normalização não significa criar o maior número possível de tabelas. A estrutura deve representar corretamente as regras do sistema e continuar compreensível e prática para consultar.

3. As três primeiras formas normais

3.1. Primeira Forma Normal (1FN)

Uma tabela está na 1FN quando cada campo contém um valor único e indivisível para o contexto definido, sem listas de valores dentro de uma mesma célula e sem grupos repetidos de colunas.

Exemplo: em vez de colocar “ana@email.com, ana.trabalho@email.com” na mesma coluna de e-mail, cada valor deve ser representado de maneira adequada ao modelo. Se uma pessoa puder ter vários e-mails, eles podem ser armazenados em uma tabela relacionada.

3.2. Segunda Forma Normal (2FN)

Uma tabela está na 2FN quando está na 1FN e todos os atributos que não fazem parte de uma chave dependem da chave completa — não apenas de uma parte dela. Essa regra é especialmente importante quando a chave primária é composta por mais de uma coluna.

Exemplo: em uma tabela de itens de pedido, o nome do produto depende do produto, não da combinação entre pedido e produto. Por isso, os dados do produto devem ficar em uma tabela própria.

3.3. Terceira Forma Normal (3FN)

Uma tabela está na 3FN quando está na 2FN e os atributos que não são chave não dependem de outros atributos que também não são chave. Em termos práticos, evitamos guardar em uma tabela informações que pertencem a outra entidade.

Exemplo: se cada CEP ou código de departamento determina uma descrição específica, essa descrição pode precisar ficar em uma tabela própria, relacionada pelo código, conforme as regras reais do sistema.

Resumo: 1FN organiza os valores; 2FN elimina dependências parciais de chaves compostas; 3FN elimina dependências transitivas entre atributos que não são chave.

4. Exemplo prático: clientes e pedidos

Uma estrutura organizada mantém os dados dos clientes separados dos dados dos pedidos. Cada cliente possui um identificador único, e cada pedido guarda esse identificador para indicar quem fez a compra.

Essa separação evita repetir o nome e o e-mail do cliente em cada pedido. Se o e-mail mudar, basta atualizar o registro do cliente. Os pedidos continuam ligados ao mesmo cliente por meio de id_cliente.

Por que isso ajuda?

Sem organização adequada

  • Nome e e-mail podem se repetir em muitas linhas.
  • Uma atualização pode ser esquecida em algum registro.
  • Excluir um pedido pode apagar acidentalmente a única cópia de uma informação.

Com normalização

  • Os dados do cliente ficam em um único lugar.
  • As chaves relacionam as tabelas.
  • Restrições ajudam a manter a integridade dos registros.

5. Exemplo de código SQL

O exemplo utiliza PostgreSQL 18 como referência de SGBD (Sistema Gerenciador de Banco de Dados). Os dados são fictícios e os comandos podem ser adaptados a outros bancos compatíveis.

5.1. Criando tabelas relacionadas

-- Tabela que guarda os dados de cada cliente
CREATE TABLE clientes (
    id_cliente INTEGER PRIMARY KEY,
    nome VARCHAR(100) NOT NULL,
    email VARCHAR(150) UNIQUE NOT NULL
);

-- Tabela que guarda os pedidos e referencia o cliente
CREATE TABLE pedidos (
    id_pedido INTEGER PRIMARY KEY,
    id_cliente INTEGER NOT NULL REFERENCES clientes(id_cliente),
    data_pedido DATE NOT NULL,
    valor_total NUMERIC(10,2) NOT NULL CHECK (valor_total >= 0)
);

INSERT INTO clientes VALUES
(1, 'Ana Souza', 'ana@example.com'),
(2, 'Bruno Lima', 'bruno@example.com');

INSERT INTO pedidos VALUES
(101, 1, '2026-09-10', 150.00),
(102, 1, '2026-09-12', 89.90),
(103, 2, '2026-09-13', 210.00);

5.2. Consultando os dados relacionados

-- Combina pedidos e clientes usando a chave estrangeira
SELECT
    p.id_pedido,
    c.nome,
    p.data_pedido,
    p.valor_total
FROM pedidos p
JOIN clientes c
    ON c.id_cliente = p.id_cliente
ORDER BY p.data_pedido;

Atenção: as chaves primárias e estrangeiras ajudam a identificar registros e manter os relacionamentos válidos. A estrutura final deve ser planejada de acordo com as regras reais do negócio; o exemplo é didático e simplificado.

6. Vantagens e cuidados

Vantagens

  • Reduz repetição desnecessária de dados.
  • Diminui o risco de inconsistências durante atualizações.
  • Ajuda a evitar anomalias de inserção, alteração e exclusão.
  • Deixa mais claras as relações entre entidades.

Pontos de atenção

  • Consultas podem precisar relacionar várias tabelas.
  • O modelo precisa refletir corretamente as regras do sistema.
  • É importante escolher chaves e restrições adequadas.
  • O desempenho deve ser avaliado com consultas e dados reais.
  1. Identificar as entidades e as regras do negócio.
  2. Definir chaves primárias e relacionamentos.
  3. Verificar se os atributos dependem das chaves corretamente.
  4. Aplicar as formas normais necessárias ao cenário.
  5. Testar as consultas e validar a integridade dos dados.

7. Conclusão

A normalização é uma técnica importante no projeto de bancos de dados porque ajuda a organizar as informações, reduzir duplicações e manter os dados consistentes. As três primeiras formas normais orientam a estruturação de tabelas e suas dependências. Embora uma estrutura normalizada possa exigir relacionamentos entre tabelas nas consultas, ela oferece uma base organizada e confiável para muitos sistemas. A melhor solução depende das regras do negócio, da integridade necessária e dos requisitos de desempenho.
