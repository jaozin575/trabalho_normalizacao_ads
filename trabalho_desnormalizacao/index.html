Desnormalização de Banco de Dados

Como a repetição controlada de informações pode simplificar consultas — e quais cuidados são necessários.

Publicado em: [DD/MM/AAAA] · Última revisão: [DD/MM/AAAA]

1. Um problema real: relatórios demorados

Imagine uma loja virtual que recebe muitos pedidos. A equipe precisa consultar diariamente um relatório com o número do pedido, a data, o nome do cliente e o valor total. Essas informações ficam em tabelas diferentes, então a consulta precisa relacioná-las. Se o relatório for muito acessado e os dados forem grandes, essa operação pode contribuir para uma demora — mas é necessário medir antes de concluir que esse é o problema.

Neste artigo, vamos entender como a desnormalização pode ajudar em alguns casos, usando um exemplo pequeno e dados fictícios. Também veremos que copiar informações cria uma responsabilidade: manter as cópias atualizadas.

2. O que é desnormalização?

A normalização organiza os dados em tabelas relacionadas para reduzir repetições e evitar problemas ao inserir, alterar ou excluir informações. Por exemplo, o nome e o e-mail de um cliente podem ficar registrados apenas na tabela de clientes.

A desnormalização é uma decisão de projeto em que adicionamos dados repetidos ou informações já calculadas a uma estrutura específica para simplificar certas consultas ou melhorar o desempenho. Ela deve ser considerada depois de analisar as consultas e medir o problema, e não apenas por suposição.

Em palavras simples: normalizar ajuda a evitar cópias desnecessárias. Desnormalizar aceita algumas cópias, de forma planejada, quando existe uma vantagem que compensa o trabalho extra de manutenção.

3. Exemplo prático: pedidos de uma loja virtual

Primeiro, separamos os dados do cliente dos dados do pedido. Essa organização evita repetir o nome e o e-mail do cliente em todos os pedidos.

Para mostrar o relatório, o banco relaciona as duas tabelas. Se a consulta for uma das partes mais acessadas do sistema, uma alternativa seria manter uma tabela auxiliar de relatório que também guarde o nome do cliente. Isso é um exemplo de desnormalização.

A vantagem possível é consultar o relatório sem buscar o nome em outra tabela. A desvantagem é que, se o nome mudar na tabela original, a cópia também precisa ser atualizada. Caso contrário, o relatório poderá exibir uma informação antiga.

4. Exemplo de código SQL

O exemplo usa PostgreSQL 18 como referência de SGBD (Sistema Gerenciador de Banco de Dados). Os comandos apresentados são básicos e podem ser adaptados a outras versões compatíveis. Os dados são fictícios.

4.1. Criando as tabelas normalizadas

-- Tabela que guarda os dados dos clientes
CREATE TABLE clientes (
    id_cliente INTEGER PRIMARY KEY,
    nome VARCHAR(100) NOT NULL,
    email VARCHAR(150) UNIQUE NOT NULL
);

-- Tabela que guarda os pedidos e liga cada pedido ao cliente
CREATE TABLE pedidos (
    id_pedido INTEGER PRIMARY KEY,
    id_cliente INTEGER NOT NULL REFERENCES clientes(id_cliente),
    data_pedido DATE NOT NULL,
    valor_total NUMERIC(10,2) NOT NULL
);

INSERT INTO clientes VALUES
(1, 'Ana Souza', 'ana@example.com'),
(2, 'Bruno Lima', 'bruno@example.com');

INSERT INTO pedidos VALUES
(101, 1, '2026-09-10', 150.00),
(102, 1, '2026-09-12', 89.90),
(103, 2, '2026-09-13', 210.00);

-- Consulta normalizada: relaciona pedidos e clientes
SELECT p.id_pedido, c.nome, p.data_pedido, p.valor_total
FROM pedidos p
JOIN clientes c ON c.id_cliente = p.id_cliente
ORDER BY p.data_pedido;

4.2. Criando uma tabela auxiliar desnormalizada

-- Tabela auxiliar com uma cópia do nome para o relatório
CREATE TABLE pedidos_relatorio (
    id_pedido INTEGER PRIMARY KEY,
    id_cliente INTEGER NOT NULL,
    nome_cliente VARCHAR(100) NOT NULL,
    data_pedido DATE NOT NULL,
    valor_total NUMERIC(10,2) NOT NULL
);

-- Copia os dados atuais para a tabela de relatório
INSERT INTO pedidos_relatorio
    (id_pedido, id_cliente, nome_cliente, data_pedido, valor_total)
SELECT p.id_pedido, c.id_cliente, c.nome, p.data_pedido, p.valor_total
FROM pedidos p
JOIN clientes c ON c.id_cliente = p.id_cliente;

-- A consulta do relatório fica mais direta
SELECT id_pedido, nome_cliente, data_pedido, valor_total
FROM pedidos_relatorio
ORDER BY data_pedido;

Abrir o script SQL completo no repositório (o arquivo deve ser publicado junto desta página).

Atenção: este exemplo faz apenas uma carga inicial. Ele não atualiza a tabela auxiliar automaticamente quando as tabelas originais mudam. Em um sistema real, seria preciso planejar e testar uma rotina de atualização. A desnormalização também não garante que a consulta ficará mais rápida: isso precisa ser medido.

5. Vantagens, desvantagens e cuidados

Possíveis vantagens

  • Relatórios podem ter consultas mais simples.
  • Alguns relacionamentos ou cálculos podem ser evitados na leitura.
  • Estruturas preparadas podem ajudar em consultas muito frequentes.

Possíveis desvantagens

  • O mesmo dado pode ficar salvo em mais de um lugar.
  • As cópias podem ficar diferentes se não forem atualizadas.
  • Há mais espaço ocupado e manutenção a fazer.
  1. Identificar qual consulta está lenta.
  2. Medir o desempenho antes e depois da mudança.
  3. Definir como os dados repetidos serão atualizados.
  4. Usar dados fictícios em exemplos públicos.
  5. Documentar a decisão e os riscos aceitos.

6. Conclusão

A desnormalização pode ser útil quando existe uma necessidade real de melhorar consultas ou relatórios. Ela permite guardar algumas informações repetidas para simplificar a leitura, mas também aumenta a responsabilidade de manter os dados corretos. Por isso, deve ser aplicada com planejamento, depois de analisar o problema e medir o desempenho. O mais importante é encontrar um equilíbrio entre velocidade, organização e consistência dos dados.
